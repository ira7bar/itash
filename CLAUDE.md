# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

תשחץ הארץ (Tashbetz Ha'aretz) — a live, collaborative solver for the weekly Haaretz Hebrew crossword. This whole working directory is a single git repo (remote `https://github.com/ira7bar/itash.git`, deployed via GitHub Pages at `https://ira7bar.github.io/itash/`) with two things living side by side in it:

- **The PWA** — the actual shipped product, living directly at repo root (`index.html`, `src/`, `style.css`, `service-worker.js`, `manifest.webmanifest`, `icons/`, `fonts/`): a static, no-build-step Progressive Web App that loads a dated `puzzle_YYYY-MM-DD.json`/`.png` pair and lets one or more people solve the grid together in real time.
- **The weekly parsing pipeline** — also at root (`parse_puzzle.py`), an offline, one-off tool that turns a given week's `tashbetz.pdf` into that `puzzle_YYYY-MM-DD.json` + `.png` pair. `debug/` and `dev/` are both gitignored scratch workspaces (not shipped, not tracked): `debug/` holds each week's source PDF plus the many one-shot `check_*.py` / `*_check.json` scripts written while reverse-engineering the PDF's layout (grid detection, arrow/clue routing, split cells, rotation, etc.) — throwaway investigation artifacts, not a maintained tool suite, don't assume they still run cleanly or need to. `dev/` holds the Playwright verification scripts (see Testing below).
- **`docs/ideas.md`** — tracked (unlike `dev/`/`debug/`), a running log of feature discussions deliberately deferred to a future session rather than built on the spot. Check it for open context before starting unprompted work; add to it when a design conversation ends in "later, not now" rather than losing that reasoning.

Solo development, no PR workflow — changes get pushed straight to `main`.

When asked to "fix the app" or work on the solving experience, the work is almost always in `src/`/`index.html`/`style.css`. Parsing work only concerns generating/repairing a given week's puzzle data.

## Deploying a new week

```
python parse_puzzle.py path/to/tashbetz.pdf --page 3 --out puzzle_YYYY-MM-DD.json --image-out puzzle_YYYY-MM-DD.png
```

(`meta.source` in the output is whatever `pdf_path` string was passed, and `meta.image` is auto-derived from `--image-out`'s basename — so run this from repo root with a same-named copy of the PDF there, e.g. `tashbetz.pdf`, so `meta.source` stays a clean filename rather than a `debug/...` path.)

The puzzle filenames carry the week's date and are **not** a fixed name — after generating the new pair, two places must be updated by hand for each deploy, and `git rm` the previous week's `puzzle_*.json`/`.png`:
- `src/main.js`'s hardcoded `fetch("puzzle_YYYY-MM-DD.json", ...)` call. This same filename also becomes `puzzle.meta.week` right after the fetch (client-side, not part of the parser's own output schema) — see `storage.js`'s note below for why solo progress needs it — so there's no separate per-week step for that, just this one existing edit.
- `service-worker.js`'s `CACHE_NAME` (bump the version suffix so clients pick up the change — see below). Its fetch handler already matches puzzle files by pattern (`/^puzzle.*\.(json|png)$/` on the basename), so it does *not* need a per-week edit.

Extracts everything from the PDF's vector/text layers — no OCR, no image processing. Documented in detail in the module docstring at the top of `parse_puzzle.py`:

- **Grid structure**: clue cells are solid light-blue fill rectangles (`BLUE_FILL` in `parse_puzzle.py`); any grid cell overlapping one is `blocked`, everything else is `playable`.
- **Clue text**: bucketed by cell, then by which fill rectangle within the cell (some cells hold two stacked clue boxes divided by a rule line, not one multi-line clue) — see `grid[r][c].clueParts` vs the combined `grid[r][c].clue`.
- **Word runs**: derived purely from grid geometry (maximal horizontal/vertical strips of ≥2 contiguous playable cells), not from the PDF's own clue numbering.
- **Known limitation**: a handful of cells route their clue via a bent/hook arrow to a non-adjacent run (e.g. a vertical word starting in the top row, with no cell above it to hold the clue). Adjacency-based matching can't catch these; a dozen or so runs typically come out with no clue each week (reported in the script's own output and in `puzzle.warnings.run_ids_without_clue`) and ship as-is — this has consistently been treated as an acceptable known limitation rather than something to hand-fix before deploying, and there is currently no in-app editing mode (one existed once; see `git log -- puzzle.json` around "Pivot to image-overlay rendering; remove edit mode").

Output schema (`puzzle_YYYY-MM-DD.json`): `meta` (rows, cols, source PDF/page, rendered image dimensions, and the grid's pixel origin/cell-size within that image — this is what lets the PWA overlay be purely percentage-based, see below), `grid` (2D array of cell type + clue text), `words` (id, direction, ordered list of `[row, col]` cells), `warnings`.

The `check_*.py` scripts and matching `*.json` outputs under `debug/` were ad hoc tools for validating specific pieces of this extraction (arrow positions, glyph rotation, split-cell detection, etc.) against a specific PDF. Treat them as reference/history, not a CLI surface to keep working.

## The PWA

No npm, no bundler, no build step — plain ES modules loaded directly by the browser (`<script type="module" src="src/main.js">`). Firebase's SDK is likewise loaded as native ES modules straight from Firebase's CDN, and only fetched once a live room is actually created/joined — solo solving never touches the network. This "no build step" property is deliberate; don't introduce a bundler/framework without discussing it first.

### Running it locally

Serve the repo root with any static file server (e.g. `python -m http.server 8123`) and open `index.html`. The `dev/` scripts (see Testing below) assume it's reachable at `http://localhost:8123`.

### Core architecture

The grid is a **rendered image of the actual PDF page**, not a reconstructed CSS grid — clue text, dividers, borders, and the source's own direction arrows all come through pixel-perfect because none of it is redrawn. `render.js` positions a transparent, purely percentage-based interactive overlay (`div.cell` per grid cell) on top of that `<img>`, using `puzzle.meta`'s origin/cell-size fields converted to percentages of the image's own box. Percentages (not pixel math) mean the overlay stays aligned at any viewport size or native pinch-zoom level with zero resize handling.

Module responsibilities (`src/`):
- **`model.js`** — all grid/word-run/state logic, deliberately DOM-free so it could survive a future rendering-layer swap unchanged. Owns cell selection and typing/backspace, and the clue-cell reverse index — see **Typing & selection model** below for the actual rules, they're more subtle than a one-liner.
- **`render.js`** — builds the cell overlay once (also marking clue cells that resolve to a word as `.clue-tappable`, for the cursor affordance), then re-renders per-cell state (letter, active/in-word/blocked classes, and other participants' presence tints — see below) on every change. Also owns the chat panel's DOM output (`renderRoster`, `renderChatMessages`, `renderChatToggle`) for the same reason: turning state into DOM, regardless of which feature.
- **`interaction.js`** — wires DOM events to `model.js`: click-to-select (including clue-cell taps), the hidden-input trick for summoning the mobile keyboard, arrow-key navigation, viewport panning (see **Viewport / pan-to-follow** below), and the share/join/leave-room UI.
- **`hebrew.js`** — normalizes every typed character before it's committed: English-keyboard-layout fallback (maps by physical key position per the Hebrew SI 1452 layout, including the three letters that live on punctuation keys — comma/period/semicolon), then collapses final-form letters (ך/ם/ן/ף/ץ) to their regular form, since a crossword cell can't reflect "is this word-final" when it's often also a middle cell of the crossing word.
- **`storage.js`** — solo progress autosave to `localStorage`, keyed by `puzzle.meta.week` (the puzzle's own dated filename, set by `main.js` right after fetching it) — deliberately **not** `meta.source`/`page`, which come from the source PDF and stay constant week to week (see parse_puzzle.py's docs), so keying off those would load last week's answers into this week's differently-shaped grid on solo open instead of starting fresh.
- **`share.js` / `sync.js`** — live collaborative rooms via Firebase Realtime Database. `sync.js` is the *only* module that touches Firebase; everything else deals in plain answer maps, so the backend could be swapped by rewriting this one file. A room's full state is only ever overwritten wholesale at creation time; every ongoing edit (`pushAnswerCell`, `pushAnswerHue`, `pushPresence`, `pushMessage`) writes a single child path, never the whole room — concurrent edits from different people must never clobber each other. `main.js` wraps these pushes with one quiet retry (`pushWithRetry`) to cover a transient mobile network blip, and re-subscribes on `visibilitychange` to survive backgrounded tabs dropping their WebSocket.
- **`presence.js`** — this device's own live-room identity: a random `userId`, a random hue, and (once chosen) a display name, all persisted in `localStorage` (separate from any one puzzle's progress, unlike `storage.js`) so the same person keeps the same color/name across reloads instead of looking like a new participant every time. Unlike id/hue, the name has no random default — `getUserName()` returns `null` until someone actually sets one (see **Chat** below). See **Presence (who's looking at what)** below.
- **`chat.js`** — DOM-free live-room chat state (message list, unread count), same discipline as `model.js`. See **Chat (live-room messaging)** below.
- **`chat-interaction.js`** — wires the chat panel's DOM events (open/close, send, the lazy name prompt) to `chat.js`/`presence.js`, parallel to how `interaction.js` wires the grid — kept as a separate file since chat is an unrelated concern from grid gestures.
- **`main.js`** — wires everything together, owns the room join/leave/create lifecycle and the puzzle-complete celebration trigger.
- **`firebase-config.js`** — public client config (not a secret — access control is via Realtime Database security rules, not by hiding this). Room IDs are random base36 strings embedded in the URL hash (`#room=xxxxxx`); opening a room's link/code joins that live room and overrides local progress, same as any explicit "load this" action.

Service worker (`service-worker.js`) does app-shell caching for offline use (cache-first for the shell, network-first-with-fallback for the dated `puzzle_*.json`/`.png` pair, matched by filename pattern, so a new week's puzzle is picked up when online). Bump `CACHE_NAME` whenever shipping a shell file change (including the weekly `main.js` fetch-path edit) so clients pick it up.

### Presence (who's looking at what)

In a live room, every participant's currently-active WORD is lightly tinted on everyone else's screen, with their one exact current cell tinted more strongly on top — in a color unique to that person, so it's visible at a glance who's working on what and exactly where within it. This mirrors how the app already distinguishes "the word you're in" from "the exact cell you're on" for your OWN cursor (`--in-word-bg` vs `--active-bg`), just applied to everyone else's. Solo solving never touches this at all (no `roomId`, no writes).

- **Identity, not accounts**: `presence.js` hands out a random `userId` plus a random hue on first use and persists both in `localStorage`, so reloading the page keeps the same color instead of minting a new "participant" each time. Only a *hue* is randomized (`presenceWordTint`/`presenceLetterTint` fix saturation/lightness/alpha) rather than a full color, so there's no chance of landing on something too dark or too pale to read the letter underneath. Both shades are deliberately much lighter than the own-cursor pair they mirror (0.16/0.30 alpha here vs 0.28/0.55 for `--in-word-bg`/`--active-bg`) — this is ambient "who's working on what" texture, not a primary highlight, so it shouldn't compete for attention.
- **Hue spacing on first assignment**: a hue is permanent once picked (that's the whole point — see above), so this can only ever help a genuinely new device, and only the one time it matters most: `main.js` checks `hasUserHue()` before generating one, and if this device has never had one *and* it's opening a room link (`getRoomIdFromUrl()`), it does a one-time, non-subscribing read of that room's current presence (`peekRoomPresenceHues` in `sync.js`) and passes those hues to `getUserHue` as `avoidHues`. `pickFarHue` then samples several random candidates and keeps whichever lands farthest (by circular distance) from all of them, instead of a plain uniform pick that could easily land close enough to an existing participant's hue to be hard to tell apart — a real risk with only a handful of people spread across 360 degrees, worse once washed out to these tints' own light alpha. Falls back to plain random whenever there's nothing to avoid (no room link, a brand-new empty room, or the peek itself fails — wrapped in a try/catch, same "don't let a flaky network take down the app" reasoning as everywhere else network calls happen here). Two ALREADY-established devices whose hues happen to collide when they later end up in the same room aren't fixed by this — there's no retroactive path that wouldn't break "same color across reloads."
- **Sync shape**: each device writes just its own child path, `rooms/{roomId}/presence/{userId}` = `{ row, col, hue, direction }` (`pushPresence` in `sync.js`), same one-child-path-per-writer reasoning as `pushAnswerCell`/`pushAnswerHue` — concurrent presence updates from different people must never stomp each other. `direction` (`state.activeDirection`, possibly `null`) is what lets every OTHER client resolve that person's whole active word locally (`getWordCellsForPresence` in `model.js`) rather than shipping a cells array over the wire each time. It rides along on the same whole-room subscription everything else uses (`subscribeRoom`), so there's no separate presence listener to manage.
- **Cleanup**: `pushPresence` arms an `onDisconnect().remove()` on every write, so a closed tab, dead network, or locked phone doesn't leave a stale cursor on the grid forever; the ordinary "leave room" button additionally calls `clearPresence` directly, so a deliberate leave clears instantly rather than waiting for Firebase to notice the disconnect.
- **What triggers a push**: `main.js`'s `syncPresence` runs off the same `onChange` every other state change already funnels through, but only actually writes when `state.activeCell`/`state.activeDirection` differ from what it last pushed (`lastPushedCell`) — `onChange` fires on every keystroke, not just cell-to-cell navigation, and re-writing unchanged presence would be pure noise. Direction is part of that comparison, not just row/col, because re-tapping a dual-direction start cell can flip direction without moving the active cell at all (see `selectCell` in `model.js`) — exactly the case where other participants' view of "which whole word is highlighted for this person" needs to update. `lastPushedCell` is reset to `null` on join/leave/resync so a room-identity change always forces one fresh push.
- **Rendering**: `applyRemotePresence` in `model.js` rebuilds `state.presence` from a room snapshot, dropping this device's own entry — a participant never needs a presence tint for their own cursor, since the existing `.active`/`.in-word` classes already show it. `render.js` builds two cell→hue maps (one for each remote participant's whole word, one for their exact current cell) and applies whichever's stronger as a `box-shadow` (via a per-cell `--presence-color` custom property), deliberately *not* `background` — `.active`/`.in-word` already set `background` through CSS classes, and box-shadow layers on top of that independently instead of fighting over the same property, so a cell someone else is also working in still shows your own active/in-word highlight underneath their tint.

### Answer authorship (who filled in what)

Every filled cell in a live room carries a very light, permanent tint of whichever hue last wrote it — `state.answerHues[r][c]`, parallel to `state.answers[r][c]`, rendered via `answerAuthorTint` in `presence.js` (`hsla(hue, 65%, 50%, 0.10)`, deliberately lighter than either presence tint: this one's *permanent* on every filled cell rather than tied to one participant's current cursor, so it needs more headroom before a busy multi-author grid starts reading as noisy rather than clean). Solo solving never renders this (`updateGrid` gates it on `state.roomId`) — there's only ever one possible author, nothing to show.

- **Sync shape**: `rooms/{roomId}/answerHues/{row}_{col}` = hue, written via `pushAnswerHue` in `sync.js` — a separate path from `answers`, not a combined `{letter, hue}` value at the same path, so the `answers` path's shape never changes for anything only reading that. `setAnswerHue` is called locally on every answer edit regardless of room state (see `onAnswerCellChange` in `main.js`), so it's already correct the instant a room is created from it; only the sync write and the render are gated on actually being in one.
- **Rendering layered with presence**: both `.presence-tint` and `.author-tint` are semi-transparent inset `box-shadow`s on the same cell, so they need an explicit combined CSS rule (`.cell.author-tint.presence-tint`) to stack both shadows rather than one clobbering the other — see the comment above it in `style.css`.
- **A cell's hue is `null` until it's been synced to some room** — meaning "written before this device ever joined any room," not "nobody." This is exactly the signal `ownAnswersForNewRoom` in `model.js` uses to fix a real leak: creating a brand-new room used to seed it from *every* currently-filled cell, including leftovers from a *previous* room you'd just left (its collaborators' answers, not yours) — since leaving a room doesn't clear the board (see `leaveRoom`'s "not a puzzle reset" below). `ownAnswersForNewRoom(state, hue)` only includes a cell if its hue is `null` (genuinely local/solo authorship) or matches the creator's own `hue` (their own past contributions, even from a room they've since left) — so solo progress and your own prior work both still carry into a room you create, but nobody else's collaborative answers from some other room ever silently do.

### Unsure marking (pencil-gray letters)

Long-pressing a cell flags it "unsure" — the letter renders in a light pencil-gray (`--unsure-gray`, `#bfbfbf`, chosen against the actual puzzle scan background) instead of the ordinary black, and pressing again clears the flag. Solo-only concept-wise (it works without a room), but syncs and persists like everything else here. An earlier version of this same idea used a red dashed underline instead of recoloring the letter — replaced because a gray "pencil" letter reads as "written provisionally," where a red underline reads as "this is wrong," which isn't the intent.

- **State shape**: `state.unsureCells[r][c]`, a boolean grid parallel to `answers`/`answerHues` — a per-cell flag, not a per-word one. It started out per-word (a `Set` of word ids), but that couldn't express "just this one letter," which turned out to matter once long-press needed the same whole-word-vs-single-letter split typing already has (next bullet).
- **Whole word or just one letter, exactly like editing does** (`toggleUnsure` in `model.js`): a long-press reuses `wholeWordCandidates` — the very function `selectCell` itself uses to decide whether tapping a cell enters whole-word mode or edits just that letter — so the SAME cells that are "whole-word" for typing (a word's start cell, or its end cell if not empty) are "whole-word" for the unsure toggle too; any other (mid-word) cell toggles only itself. Toggling a whole word flips every one of its cells to the SAME state, based on whether they're already *all* gray — "already all flagged" is what reads as "toggle back off" (mirroring "a fully-filled word, tapped again, means start over"), anything else (none, or a mixed partial state) means "flag the rest too."
- **Resolving which word a long-press on a boundary cell means** (`resolveWordForToggle` in `model.js`): if the currently-*active* word (whatever was already selected before this press started) covers the pressed cell, that's the one — this handles a crossing cell unambiguously by using whichever direction you were already looking at, the same "another hint for ambiguous cases" reasoning `selectCell` itself uses elsewhere. Otherwise (long-pressing a fresh intersection cold, with neither word selected yet) it falls back to horizontal-then-vertical, an honest limitation for that one case — long-press only ever needs to be unambiguous when you tapped the word you meant first.
- **Timing subtlety**: the long-press timer starts on `pointerdown` in `interaction.js` and fires (checking `resolveWordForToggle`) *before* that same press's own eventual `click` → `selectCell` call would update `state.activeCell`/`activeDirection`. That's deliberate, not a bug to fix — it means the toggle always resolves against whatever word was active *before* this press began, i.e. the word you were already reviewing when you decided to flag it. The `click` handler still fires normally afterward and selects the pressed cell as usual, same as any other tap.
- **Rewriting a gray letter makes it black again** (`typeLetter`/`backspace` in `model.js`): writing to a cell — typing over it, or backspacing it blank — always clears that cell's own unsure flag, regardless of the rest of its word. Retyping a letter is a vote of confidence in it specifically, and the flag being per-cell means clearing it never has to touch any other cell in the word. Backspacing to blank clears it too, for the same reason `clearBoard` already does board-wide: an empty cell has no answer left to be unsure about.
- **Rendering**: trivially `state.unsureCells[r][c]` (`updateGrid` in `render.js`) — no more cross-referencing which word(s) cross a cell the way the old per-word Set needed, since the flag already lives on the exact cell being rendered.
- **Sync shape**: `rooms/{roomId}/unsure/{row}_{col}` = `true` (or deleted, not `false`, for "no longer unsure"), written via `pushUnsureFlag` in `sync.js` — one path per cell, same per-writer-never-clobbers reasoning as `answerHues`. Unlike `answerHues`, there's no per-user authorship to filter on a new room's seed — `flattenUnsure(state)` seeds a brand-new room from whatever this device currently has flagged, wholesale, matching the original (pre-removal) design's behavior rather than adding `ownAnswersForNewRoom`-style filtering for a case that's never actually come up in practice.
- **Persistence**: solo progress persists it too (`storage.js`, alongside `answers`), as the same nested-array shape `answers` itself already uses.
- **Clearing**: `clearBoard` wipes every unsure flag along with every answer — "unsure about this answer" has no meaning once the answer itself is gone — and returns the cleared cells so `main.js` can sync each removal individually, same discipline as the cleared answers.
- **Multi-touch (pinch-zoom) must not start or leak a long-press**: `pointerdown` bails (and cancels any pending press) unless `e.isPrimary` — a second finger touching down mid-press is the start of a pinch, not a second long-press. This isn't just "ignore the second finger": a naive version that only guarded the *first* branch still let a second pointerdown overwrite `pressTimer`'s reference without clearing the original `setTimeout`, so the first finger's now-untracked timer fired anyway a few hundred ms later, regardless of the gesture — reported as "pinch-to-zoom randomly toggles unsure mode." `pressStart` also carries the originating `pointerId`, and `pointermove`/`pointerup`/`pointercancel`/`pointerleave` all check it matches before reacting, so a second pointer's own up/cancel/leave can't be mistaken for the first one's.

### Copying a clue's text

Long-pressing a clue (blocked) cell copies that clue's text to the clipboard instead of toggling unsure — the same long-press gesture branches on `isBlocked` in `interaction.js`. Reported by a user on iOS, where the OS's own copy/paste affordances make "just select the text" impossible here (it's a rendered image, not real text), so this is the only way to get a clue's wording out of the app at all — into a search engine, a group chat, wherever.

- **Split-cell reuse**: resolves which word's clue to copy with the exact same `resolveClueTapWord` the ordinary tap-to-jump click handler already uses — top half of a dual-direction clue cell is the horizontal clue, bottom half vertical (see `_split_dual_direction_clues` in `parse_puzzle.py`), evaluated against the Y position of the press's *start* (`pointerdown`), not wherever the pointer happens to be when the timer fires.
- **What gets copied**: `word.clue`, the same already-split text the app renders for that direction — not the combined `grid[r][c].clue` (which would incorrectly include both stacked clues for a shared cell). A run with no matched clue (the parser's known hook-arrow limitation) has `clue: null`; long-pressing it copies nothing.
- **Feedback**: `navigator.clipboard.writeText`, same as the room-share link (`shareRoomUrl` in `share.js`), with the identical `window.prompt` fallback for a denied/unsupported clipboard — but since there's no button here to swap a label on, a transient toast (`#clue-toast`) shows what got copied for ~1.8s. The fallback prompt already displays the text on its own, so no toast in that branch.
- **Click still fires afterward**: same as the unsure-toggle long-press, this doesn't suppress the click that follows — a long-press-then-release on a clue cell both copies its text AND jumps to that word, exactly like an ordinary tap would.

### One-time hint for the unsure long-press

Neither the unsure-marking nor the copy-clue long-press has any visible affordance in the UI — nothing on screen suggests holding a cell does anything — so `#unsure-hint-banner` nudges toward the first of those once, the first time the app is ever opened on a device.

- **Placement**: a real element in normal document flow, first child of `#grid-wrap` above `#grid` — deliberately not an overlay on top of the puzzle image, so it never covers actual playable cells while it's showing. Dismissing it (`hidden = true`) fully reclaims that space rather than just hiding content in place, since it's gone for good afterward anyway.
- **Scope**: shown once per *device*, not once per puzzle — `hasSeenUnsureHint`/`markUnsureHintSeen` in `main.js` use a plain, un-namespaced `localStorage` key (`tashbetz:seen-unsure-hint`), deliberately not scoped by `puzzle.meta.week` the way `storage.js`'s solo progress is. Scoping it per-week would re-show "here's a feature you already know" every single Thursday when a new puzzle loads, which defeats the point — once dismissed, it should stay dismissed across every future week too, the same device-scoped-not-puzzle-scoped reasoning `presence.js`'s userId/hue already use.
- **Entirely independent of puzzle/room state**: no `state`, no `onChange`, no model.js involvement — wired directly in `main.js` as a self-contained show-once/dismiss-once block, since there's nothing here for `interaction.js`'s state-driven wiring to coordinate with.

### Chat (live-room messaging)

A collapsible bottom sheet on mobile (toggle FAB over the grid, unread badge, slides up over the bottom of the screen) that docks instead as a persistent 320px sidebar past `900px` width (see the `@media (min-width: 900px)` block in `style.css`) — same panel/markup either way, CSS-only breakpoint, no separate component. Solo solving never touches any of this, same as presence — the panel/toggle stay `hidden` whenever `state.roomId` is null (`refreshRoomUi` in `main.js`).

- **Sync shape**: each message is its own new child under `rooms/{roomId}/messages/{pushId}` — `{ userId, name, hue, text, ts }`, `ts` a `serverTimestamp()` — written via `pushMessage` in `sync.js`. Different from `pushAnswerCell`/`pushPresence`'s one-fixed-path-per-writer: many different people write to this same list over time, so each message needs its own server-generated key (`push()`) rather than a shared per-user slot, but the underlying rule is the same — nobody overwrites something another participant wrote. `applyRemoteMessages` in `chat.js` treats every snapshot as a full, authoritative replace (same reasoning as `applyRemoteAnswers`), sorting by `ts` since Firebase doesn't guarantee key order across writers.
- **No message history trimming.** RTDB has no built-in pagination and this doesn't do its own — acceptable for now (a room is typically one solving session's worth of chatter), flagged here rather than silently forgotten if it ever needs revisiting.
- **Unread badge**: `chat.js`'s `chatState` tracks `seenCount` (how many messages existed the last time the panel was open); `unreadCount(chatState, selfUserId)` counts messages past `seenCount` that *aren't your own* — your own sent messages must never bump your own badge. `seenCount` only advances while `chatState.open` is true, so messages arriving while the panel is closed stay counted until it's opened; opening it (`openChat`) immediately catches `seenCount` up, clearing the badge. This works without diffing individual message ids because messages are append-only and never reordered — a plain index scan from `seenCount` onward is sufficient.
- **Surviving a reload**: `chatState` itself is rebuilt from scratch on every page load (`seenCount` starts at 0 again), which would otherwise re-flag an entire already-read backlog as unread on every reload. `bindChatRoom(chatState, roomId)` — called in `main.js`'s `joinRoom`, before subscribing, since the first snapshot can arrive as part of that subscription's own setup — marks `seenCount` as needing to be *derived*, not assumed, on the next `applyRemoteMessages` call: it's recomputed from a "read up through this timestamp" marker persisted per room in `localStorage` (`tashbetz:chat-seen:{roomId}`, saved every time `seenCount` legitimately advances), rather than starting from 0. A timestamp, not a raw count, since the in-memory array is rebuilt from nothing on reload anyway — "read up through this moment" still means the same thing once the fresh snapshot arrives; a stale count wouldn't.
- **Identity reuse**: no separate chat-specific identity — messages carry the same `userId`/`hue` as presence. Display name is the one new piece of identity (`presence.js`'s `getUserName`/`setUserName`), persisted the same way as `userId`/hue (device-scoped `localStorage`, not puzzle-scoped) so a chosen name survives reloads and future weeks. Presence writes (`pushPresence`) now also carry `name`, which is how the roster ("who's here") gets it for free — `renderRoster` in `render.js` just reads `entry.name` off the same `state.presence` map the grid tints already use, no separate roster sync.
- **Lazy name prompt**: no name is collected on join. `chat-interaction.js`'s `wireChat` opens the name modal on `chatInput`'s `focus` event when `getUserName()` is still `null` — which, with no branching needed, covers both surfaces: on mobile that's the instant the sheet opens (`openPanel` already focuses the input), and on the always-visible desktop dock it's an ordinary click into the input, since there's no separate "open" moment there to hook. The `chatForm` submit handler keeps its own `getUserName()` check too, as a fallback for anyone who dismisses that prompt (backdrop click) and sends anyway — that path still holds the typed text (`pendingText`) until the name is confirmed, then sends it, so nothing is lost or sent anonymously. Tapping your own roster chip reopens the same modal, prefilled, to change the name later.
- **Renaming and presence**: changing your name doesn't move the active cell, so it can't rely on a cell-position diff to know to re-push. `syncPresence` in `main.js` includes `name` in its own "did anything change" comparison (`lastPushedCell`) precisely so a rename alone (no cell movement) still triggers a fresh `pushPresence` — `onRenameSelf` just calls the ordinary `onChange`, no special-cased push path.
- **Firebase security rules caveat**: `sync.js`'s Realtime Database rules live only in the Firebase console (see `firebase-config.js`'s comment), not in this repo. If those rules are scoped to specific known paths rather than a wildcard under `rooms/{roomId}`, writes to the new `messages` path need a rule added there too, or they'll be silently rejected.

### Typing & selection model

None of this is validated against a solution key — there isn't one; the app only ever knows "filled" vs "blank", never "correct." That constraint shapes several of these rules.

- **Entering a word** (`selectCell`): tapping a word's **start** cell always enters whole-word typing mode for it, regardless of how full it already is. Tapping its **end** cell enters backspacing mode, but only if it has at least one letter to delete. Any other cell (mid-word, or an end cell of an empty word) is unambiguous and just edits that one letter directly. A cell that's the start of one direction *and* the end of the other, or the start of both an across and a down word, is resolved by whichever candidate is unambiguous, or by re-tapping to flip between them.
- **The active cell never gets redirected on selection** — tapping (or clue-jumping to) a word's start always lands exactly there, letter-for-letter where you tapped, even if that cell already has a letter in it. This is deliberate: silently moving the cursor away from what was literally tapped is surprising, especially combined with auto-pan (see below) — better to "waste" a keystroke reconfirming an already-filled cell than to jump the view somewhere the user didn't point at.
- **Typing forward** (`typeLetter` / `nextTypeIndex`) always fills whatever the active cell currently is, then moves the *next* keystroke to the plain next cell in the word, in order — it never skips ahead over a cell that's already filled (e.g. via a crossing word). This was tried the other way (skip to the next blank cell) and reverted: people are used to writing whole words straight through the way they would on paper, and having the cursor jump around based on what a crossing word had already filled in was surprising. At the word's actual last cell, it stays put.
- **A fully-filled word, tapped again, means "start over."** Since there's no correctness checking, a 100%-filled word being tapped again is almost always "this was wrong, let me redo it" — so it enters ordinary sequential whole-word typing from its first cell, overwriting every letter in order, not a no-op.
- **Backspace never skips either.** It's deliberately kept simple and literal — clears the active cell if it has a letter, else steps back one cell and clears that — the same plain, literal sequencing as forward typing now uses.
- **Clue-cell taps** (`getWordsForClueCell` in `model.js`, `resolveClueTapWord` in `interaction.js`): a blocked cell can be the printed clue location for zero, one, or (for a clue cell shared between an across and a down word) two different words — reverse-indexed off `word.clueCell` at load time. When two words share a clue cell, the tap's Y position within the cell picks between them: top half is always the horizontal word's clue, bottom half always the vertical, a rule the parser validated (see `_split_dual_direction_clues` in `parse_puzzle.py`), not a heuristic. A resolved tap selects that word's start cell exactly as if it had been tapped directly (same rules as above apply from there).

### Viewport / pan-to-follow

The app deliberately does **not** implement its own zoom — it relies entirely on native OS/browser pinch-zoom (`user-scalable=yes`), never a CSS-transform zoom layer. Only *scroll position* is ever driven programmatically; two past Android bugs (see `git log`) came specifically from the app fighting the browser's own zoom/touch-action handling, so this boundary is intentional, not an oversight.

- **Native long-press-image menu is suppressed**, since Android can show its own "copy/share image" menu on an ordinary long-press (holding to scroll, typing slowly, or the unsure-marking long-press) even though the overlay sits visually on top and normally takes the touch — Android's image-menu detection wasn't reliable DOM hit-testing, so it could still fire as if the image itself were touched. Primary fix: `pointer-events: none` on `#puzzle-image` in `style.css`, taking the image fully out of hit-testing (safe since every real interaction already goes through `.cell` elements in the overlay, never the image). `contextmenu` is also still prevented on both the image and the overlay in `interaction.js`, as defense-in-depth and for an ordinary desktop right-click.
- **iOS's native text-selection loupe is a separate problem from the above**, and only showed up once `pointer-events: none` (above) moved every real touch from the image onto `#overlay-layer`/`.cell` — which, until then, had never needed their own `user-select`/`-webkit-touch-callout` rule, since nothing was ever long-pressed there before the unsure-marking and copy-clue gestures existed. `user-select: none` / `-webkit-user-select: none` / `-webkit-touch-callout: none` are set once on `#grid` (the shared ancestor of the image and the overlay) rather than repeated per element, since both properties inherit down through WebKit.
- **Tapping a clue cell** scrolls the resolved word into view with `scrollIntoView({block:"center", inline:"center"})`, since it's jumping to content that wasn't necessarily near what was tapped and full centering (both axes) is appropriate for landing somewhere new.
- **While typing, backspacing, or arrow-navigating**, the active cell is kept in view with minimal motion instead: `scrollIntoView({block:"nearest"})` (vertical; a no-op if already visible) plus `panHorizontallyToReveal` (horizontal, see below) — never `"center"`, which was tried for this and overshot badly on longer words (see below).
- **`panHorizontallyToReveal`** (in `interaction.js`) is a *hand-computed* horizontal "nearest," not the browser's own `inline:"nearest"`. It scrolls `#grid-wrap` by the minimum amount so the target cell ends up with at least one full cell's width of clearance from whichever edge it's closest to — guaranteeing the next letter (or, backspacing, the previous one) is always fully visible, not just peeking in — or does nothing if that clearance already exists. Recomputed fresh off the cell's *current* rendered width every call, so it's correct at any pinch-zoom level.
- **Why not the browser's native `inline:"nearest"` + `scroll-padding-inline`** (tried first): it silently did nothing on a word's actual last letter, since the active cell doesn't move there (nowhere left to advance to) and native "nearest" only reacts when a *fresh* target isn't already positioned — it has no way to know that's worth double-checking. Swapping in a full `"center"` for that one case (tried second) fixed the visibility but overshot on longer words, centering the single last cell mid-viewport and pushing the word's own start off-screen. `panHorizontallyToReveal` fixes both: it always recomputes from the cell's actual current position, so it's correct precisely because a word's last letter typically doesn't need to move at all (the buffer was already established scrolling *into* that cell one keystroke earlier) — genuine "nothing to do" and "silently broken" are no longer indistinguishable.
- **Caveat for anyone touching this area**: real pinch-zoom is a compositor-level visual transform, not a CSS layout change. `document.body.style.zoom` sweeps do **not** reproduce it in Playwright — they don't create genuine scrollable overflow in `#grid-wrap` at all, so a scroll bug can pass a zoom-based test while being completely broken. What does work: directly force `#grid`'s width past its container's own width (e.g. `document.getElementById("grid").style.width = "2500px"`), which creates real overflow, then use element `.click()` (which auto-scrolls its target into view) rather than raw pixel-coordinate clicks that may already be off-screen. Even so, treat any Playwright result about zoom/pan behavior as a supporting data point, not a substitute for confirming on a real phone.

### Testing

No automated test runner/CI — verification is done with one-off Playwright scripts in `dev/` (gitignored; local-only), each targeting a specific bug or feature (`test_live_two_clients.py`, `test_hidden_input_position.py`, etc.) and writing its findings to a matching `*_report.json`. They assume the app is being served locally at `http://localhost:8123` (some `*_prod.py` variants instead point at the live GitHub Pages URL, for verifying real deploys). Follow this same pattern for new manual verification: a small standalone script under `dev/` that drives the page with Playwright and asserts/reports on the specific behavior in question, rather than adding a formal test framework.

Many past mobile-specific bugs (documented in commit history and inline comments) came from Android/iOS quirks in how the OS keyboard, pinch-zoom, and long-press interact with the page — when touching `interaction.js`, `#hidden-input` positioning in `style.css`/`interaction.js`, or `touch-action`, be aware that real-device testing (not just Playwright) previously caught issues Playwright alone wouldn't.
